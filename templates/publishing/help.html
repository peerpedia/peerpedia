Find papers by subject

Use the Subject filter on the browse page to choose an arXiv category, a broad subject, or a physics archive. Combine it with a search and either sort order. Cross-listed papers appear in each of their subjects. Searching a category code or name also finds classified papers.

Uploads require one primary subject from the arXiv taxonomy. Expand Cross-list subjects to select other relevant subjects. Classification changes follow the usual submission and acceptance process; old snapshots keep their original hashes. Older papers appear under Unclassified until an author accepts a classified revision.

For CLI 0.2 or newer, set "primary_category": "cond-mat.str-el" and optionally "secondary_categories": ["hep-th"] in paper.json. List supported subjects with peerpedia categories --server https://peerpedia.dev --json. Both v1 and v2 verification manifests are supported.

Read and discover

Anyone can read without an account. On Browse, search by title, author name, or words in a paper, then sort by latest acceptance or average rating.

Click a title for its abstract, reviews, submissions, and history. Click Read paper to open the latest accepted version in a full-width reader. Use your browser’s Back button to return.

Publish a paper or note

  1. Create an account and verify your email.
  2. Choose New note to start writing Markdown with a live preview. Your private draft saves automatically; return to it from My drafts.
  3. Open Paper details to add the title, abstract, author names (one per line in publication order), and primary subject. Papers and AI-assisted notes use the same workflow.
  4. Choose Review & publish when ready. Review the document and details, choose a content license, confirm your submission rights, then publish. You become the corresponding author who decides on future changes.

Markdown headings, lists, tables, links, code blocks, and mathematical equations are supported. Use $x^2$ for inline mathematics or $$x^2$$ for a display equation. Include your references in the document.

Already have a file? Use Import Markdown inside the editor to keep working on it, or upload Markdown directly from My drafts. One UTF-8 .md document, up to 1 MB, is supported. You do not need to upload a file to write online.

Choose Edit while reading to improve an existing paper. The editor opens near your reading position and saves a private draft under My drafts. Use Paper details for the metadata and change description, then review changes before submitting. New papers publish when you confirm the initial submission. Revisions open a PR and require separate acceptance by the corresponding author.

Use Edit beside a section heading to edit only that section and its subsections. Each section has its own private draft; the icon-level Edit button still opens the whole paper. Section PRs preserve paper metadata and submit a complete paper snapshot. Unchanged sections can incorporate unrelated accepted changes when you review. If the section changed, compare and resolve it explicitly before submitting.

To improve a pending PR, choose Update PR in its conversation. Each update adds an immutable snapshot with its own hash. Earlier snapshots and comments remain available, and only the latest snapshot can be accepted. Drafts start from the latest accepted paper when opened from the reader, or from the latest PR snapshot when opened from that PR.

If saving conflicts with another tab or device, download your text before choosing which copy to keep. If a newer paper version is accepted, compare its changes and explicitly update your draft base. Your text is preserved. Browser recovery is a fallback during connection failures, not a replacement for checking the Saved indicator.

Images, PDF uploads, and multiple-file submissions are not supported yet. The online editor offers a private autosaved draft and a live preview. Check the content and attribution of AI-assisted notes before publishing.

Publication is public and permanent in the history. Once confirmed, a submission’s document and metadata are frozen. To correct them, submit a new version.

Draw diagrams in Markdown

Use CD (uppercase) inside a display equation for a simple commutative diagram:

$$
\begin{CD}
A @>f>> B \\
@VgVV @VVhV \\
C @>k>> D
\end{CD}
$$

For labelled or diagonal arrows, use a tikzcd code block. Keep the environment inside the block:

```tikzcd
\begin{tikzcd}
A \arrow[r, "f"] \arrow[d, "g"'] & B \arrow[d, "h"] \\
C \arrow[r, "k"'] & D
\end{tikzcd}
```

For general drawings, use tikzpicture (or tikz):

```tikzpicture
\begin{tikzpicture}
\draw[->] (0,0) -- (3,0) node[right] {$x$};
\draw[->] (0,0) -- (0,2) node[above] {$y$};
\draw[blue, thick] (0,0) parabola (2,1.5);
\end{tikzpicture}
```

Submitted diagrams are compiled once in the background and saved as images. Readers load those saved images without downloading a compiler. New submissions may briefly show “Preparing diagram”. The editor and upload preview still compile locally in your browser, requiring WebAssembly and an initial download of about 10 MB. No diagram source is sent to an external service.

Keep each diagram below 32 KB and each paper below 32 distinct diagrams. Editor compilation stops after eight seconds; background rendering has a thirty-second time limit. Other diagrams continue if one fails. Errors appear beside the source. After fixing a diagram in the editor, its preview updates automatically. Reload the reader to retry a failed download.

Start with basic TikZ drawing commands and tikzcd. This is not a complete LaTeX installation: only bundled libraries are available. External files, images, and arbitrary packages are not supported. Unsupported commands produce a compiler message. Use a latex code block when you want to show code without compiling it.

The reader shows diagrams without source-code controls. The Markdown source stays in the immutable submission and in its diff, and is available when editing. Rendering a diagram does not change the submission or its hash.

Propose a change

Any verified account can propose an improvement to any paper. No invitation is needed. The same process applies when you update your own paper.

  1. Open the paper’s details and choose Download Markdown to get the latest accepted version.
  2. Edit the document locally. A submission contains the whole revised document, not just the changed paragraphs.
  3. Choose Upload a change, upload your revised file, and describe what changed. Preview the document and differences, then confirm.
  4. Discuss the public proposal on its submission page. Only the corresponding author can accept or reject it; its contributor can withdraw it while it is pending.

Acceptance makes the proposed document the current version. If another change is accepted first, your proposal has an old base and cannot be accepted. Download the newest version, incorporate your changes, and submit a new proposal.

An accepted contribution appears in the contribution history. It does not automatically add the contributor to the paper’s author list.

Review and discuss

On a paper’s Reviews tab, choose 1–5 stars and write your assessment. Both are required. Each account has one editable review per paper, and authors may review their own work.

Reviews apply to the paper as a whole, across its versions. The displayed rating is the average of visible reviews. Reviews are listed newest first by their original posting time.

For a particular proposed change, use its submission conversation. Comments form a simple chronological discussion; replies, likes, and inline annotations are not available.

Discuss a passage

Select a sentence or several sentences in the reader, then choose Comment & rate. Use the plus button beside an equation, table, or code block to discuss the whole block. Small margin counts open existing discussions. The Discussions button lists all locations, including discussions from earlier versions.

A new discussion needs both a rating from 1 to 5 and a written comment. Each person has one active rating per passage. Open ⋯ beside your comment and choose Edit to update it; earlier edits remain in History. The same menu holds resolution, reporting, and PR links. These ratings are separate from the paper’s overall rating. Replies need text only and can continue at any depth. Up and down thumbs help useful comments rise; click the same thumb again to remove your vote.

Only the person who started a discussion can resolve or reopen it. A contributor can link their PR as a proposed fix. Accepting that change asks the commenter to review it; acceptance does not close the discussion automatically. Deleting a comment leaves a placeholder and preserves its replies. Use Report to ask an administrator to review a comment.

Discussions work on accepted versions and PR snapshots. An exact, unambiguous passage match carries its discussion forward. Changed passages show earlier discussions as historical links, without carrying their ratings onto the new text. Original quotations and version links remain available.

Participation requires a verified account on the website. API tokens cannot post comments, rate passages, vote, or resolve threads. Use the CLI commands below to read feedback and propose fixes. AI tools have no write access to comments, ratings, votes, or thread resolution.

Understand the history

The History tab lists accepted versions. Open an older version to read it, download its Markdown, or compare it with another accepted version. The Submissions tab also includes pending, rejected, and withdrawn proposals.

Every confirmed submission has a SHA-256 hash covering its document and submission metadata. Accepting or rejecting a submission does not change that hash. Reviews and comments are separate from the frozen document.

You can download a verification manifest alongside the Markdown. The repository’s verification instructions explain how to check them locally. A matching hash verifies content; it does not prove that a claim is correct or establish authorship.

Administrators can hide inappropriate content from public view. Hiding does not rewrite a frozen submission.

Use local files and AI tools

The Peerpedia plugin for Codex desktop can find papers, explain readers’ reactions, and help revise a paper from selected feedback. Reading needs no account. Changes stay local until you ask to submit them. Follow the linked installation guide to connect your own account when needed.

The optional command-line client lets you work in your own editor or with a local AI assistant, then upload the result. It uses the same publication and review rules as the website.

Install the client and submit from your computer

You need Python 3.12 or newer and Git. Install the client in a virtual environment:

python3 -m venv .venv
# macOS / Linux
source .venv/bin/activate
# Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pip install "git+{{ repository_url }}.git#subdirectory=cli"

Sign in on the website, open Access tokens, and create a token. Then run:

peerpedia login {{ site_url }}

Paste the token at the hidden prompt. Use a token rather than your account password. Tokens allow proposals by default; select Also allow publishing new papers only if needed. They cannot accept changes or grant administrator access.

Improve an existing paper

Replace PAPER_UUID with the identifier in the paper’s address, between /papers/ and the final slash.

peerpedia clone PAPER_UUID my-paper --server {{ site_url }}
cd my-paper
# Edit paper.md and, if needed, paper.json.
peerpedia diff
peerpedia push -m "Explain your changes"
peerpedia status

paper.md is your document. paper.json holds its title, authors, and abstract. A push creates a public, frozen proposal. The corresponding author accepts it on the website.

Publish a new paper

peerpedia init my-new-paper --server {{ site_url }}
cd my-new-paper
# Fill in paper.md and title, authors, abstract, and primary_category in paper.json.
peerpedia push -m "Initial publication"

An initial push publishes immediately; check the files before running it.

Stay up to date

Use peerpedia pull after a proposal is accepted. It refuses to overwrite local edits. If your base is stale, use peerpedia fetch, reconcile your files with the downloaded version, then run peerpedia rebase --acknowledge before pushing again.

If a push loses its connection before you get a result, use peerpedia push --retry. This resends the saved submission, even if you edited your files afterward, without creating a duplicate.

Work with a local AI assistant

Let the assistant edit your local files, inspect the diff, and use the same client to submit. For an automated runner, supply PEERPEDIA_TOKEN securely and set PEERPEDIA_SERVER to {{ site_url }}. Commands support --json for structured output. Keep tokens out of paper files and public repositories.

Read feedback and propose a fix

CLI 0.3 adds public, read-only feedback commands. Inside a cloned paper directory, run:

peerpedia feedback --all --json
peerpedia reviews --all --json
peerpedia discussion PASSAGE_ID --all --json
peerpedia comment-history COMMENT_ID --all --json

The feedback list supplies passage IDs, exact quotations, original version hashes, and current or historical locations. A discussion supplies top-level thread IDs, ratings, replies, votes, resolution, and linked PRs. --all reads every page; on discussion it includes every reply. Use feedback --submission SUBMISSION_ID to inspect a frozen PR snapshot. Public reading does not require a token.

peerpedia push -m "Clarify the explanation" --address THREAD_ID --ai-assisted
peerpedia pr PR_ID --json
peerpedia push -m "Extend the proposed fix" --pr PR_ID --expected-head FULL_HEAD_HASH --address THREAD_ID --ai-assisted

Repeat --address to link several discussions. Use the top-level thread ID from the discussion output. The first push opens a PR; the second example adds an immutable snapshot to that same PR. Obtain the full head hash with peerpedia pr. If the head or accepted base changed, fetch and review the new version before retrying. Acceptance remains a separate action for the corresponding author.

Tool submissions show your username and via CLI. Add --ai-assisted when AI helped prepare the snapshot; this label is self-declared. Use peerpedia pr-comments PR_ID --all --json for the PR conversation, or peerpedia replies THREAD_ID --all --json for replies alone. The CLI does not read private drafts or your inbox.

See the full CLI guide for retry behavior, conflict handling, and credential storage.

Your notification inbox

The bell in the main navigation opens your inbox. It shows activity on your papers and conversations, including replies, reviews, proposed changes, linked fixes, and decisions. Related updates are grouped together; your own actions do not notify you.

Choose View discussion, View PR, or View paper to open an update and mark it read. Use Unread to catch up or Mark all read to clear older activity. New activity arriving while you read remains unread. Notifications stay on the website; no notification emails are sent.

Manage your account

Choose Continue with Google to sign up or sign in using Google. New users choose a public username; the Google-verified email stays private. If you already have a Peerpedia account with that email, sign in with your password first, then open Account and connect Google.

Google-only users can choose Add a password by email in Account. Open the emailed link to set a Peerpedia password before creating CLI access tokens. You can disconnect Google after adding a password. Administrator accounts still require the Peerpedia authenticator code.

Sign in with your username or email address. You must verify your email before publishing, proposing changes, reviewing, or commenting.

If a verification email is missing, check your spam folder and use Verify email to request another. Verification links expire after 24 hours.

Use Forgot password? to receive a recovery link, or Password to change your password while signed in. Manage or revoke tool credentials under Access tokens.

Licenses and your rights

Before publishing or commenting, accept the submission and discussion agreement on the website. When publishing a new paper, explicitly choose one of six content licenses. PRs inherit that paper's fixed license, and contributors confirm their authority to submit. All choices include permission for public on-platform PRs, including rejected and superseded snapshots.

New snapshots record the license and agreement in their verification manifest. Older papers may carry a dated licensing declaration without changing their original hashes. A license does not prove ownership or academic correctness. Comments and reviews receive permission for Peerpedia display and read-only API access; they are not automatically licensed for incorporation into papers.

For CLI publication, run peerpedia licenses, set license in paper.json, and accept the agreement on the website first. The API cannot accept it on your behalf. Send a private copyright, withdrawal, or privacy request.

Chapters and cross-references

Use Add chapter in the editor to build a course. Rename and reorder chapters in the sidebar. Every chapter shares the paper's metadata, license, rating, and publication history; one PR can change several chapters.

Insert reference finds sections, equations, figures, tables, and mathematical statements in this paper, or frozen versions of other Peerpedia works. Copy reference beside a target provides its permalink. Labels such as {#sec:motivation} stay with the source when it moves.

## Motivation {#sec:motivation}

::: theorem {#thm:main}
Your statement goes here.
:::

See @sec:motivation and @thm:main.

Insert block creates theorem-like statements, proofs, captioned figures and tables, or equations. Display equations are numbered by chapter; use the unnumbered block to suppress numbering. A multi-line math display has one number.

References.bib edits or imports a standard BibTeX library shared by all chapters. Use [@wen2004] or [@wen2004, p. 12; @anotherWork]. Compact citations link to full references at the chapter's end. Unsupported fields are preserved. Broken references produce warnings and do not block submission.

Mark chapters complete to track your progress. Signed-in progress follows your account; visitor progress stays in the browser. Later edits show an Updated indicator without removing your completion mark.

CLI 0.6.0 supports chapter IDs, titles, and Markdown filenames in paper.json, plus a shared references.bib. File-format example.
